# 学科接入契约（Discipline Contract）

新学科（当前范围八科：`ming` / `ziwei` / `liuyao` / `meihua` / `xiaoliuren` / `zeji` / `liuren` / `lingqi`）照本文四步接入，不用重造轮子。
**范围仅命与卜；相科（面相、手相、堪舆）不做，不预留目录。**
契约是从已跑通的六爻里抽出来的，不是先验设计——**没有真实实现支撑的抽象一律不写进这里**。

## 一、四段管线

每科必须且只能按此四段暴露能力，段与段之间只传结构化数据：

```
chart(params)    → 机械起局排盘。纯确定性，无解读成分
analyze(chart)   → 规则推演：取用/旺衰/关系/格局/应期，输出因子与判据
narrate(analyze) → 唯一交付正文，师傅口吻自然语言
render(analyze)  → 交内核 report 出 HTML/MD，学科只提供盘数据与要点
```

硬性边界：

| 段 | 允许 | 禁止 |
|---|---|---|
| `chart` | 查内核表、算干支、装配盘 | 任何吉凶措辞 |
| `analyze` | 输出 `{因子, 权重, 判据, 所本法则}` | 成段中文断语（断语进 `data/verdicts.json`） |
| `narrate` | 把 analyze 的判据翻译成人话 | 自行推断任何新的象数结论 |
| `render` | 调内核报告模板 | 自带一套 HTML 模板 |

六爻的现状可作反例对照：它原本 `analyze` 与 `narrate` 混在 6000 行里、断语字面量 1500+ 条散在代码中，
这就是"规范不够"的具体形态。新学科不要再走一遍。

## 二、内核只提供什么

`core/yishu_core/`（当前寄居在 `core/`，M4 上收为 `Yi/core/`）：

| 模块 | 内容 | 谁在用 |
|---|---|---|
| `ganzhi_calendar.py` | 太阳视黄经求节气、立春定年界、十二节定月令、儒略日定日柱、五虎遁/五鼠遁、`find_solar_date()` 反查真实日期 | 命·卜两科全用 |
| `symbols.py` | 干支五行、生克制化、六合六冲三合三刑六破、墓库、进退神、纳音、三合局分组、纳甲支表、八宫次序 | 命·卜两科（**纳音/三合为两科共用**；命科另需藏干/大运，见 `ming_tables.py`） |
| `shensha.py` | 星煞起例与安星函数（天乙/文昌/羊刃/驿马/桃花/华盖/禄神/红艳/天喜/天德/月德） | **命·卜两科共用**（模块头已标注消费方） |
| `ming_tables.py` | 藏干十神、大运起法、命宫身宫 | 仅命科（原兼存纳音/三合/星煞，2026-09-29 已按归属拆出，见审计 B3） |
| `runtime.py` | Windows GBK 控制台 UTF-8 适配；`utf8_subprocess_env()` 让质量门子进程与父进程解码对齐 | 所有 CLI 与质量门 |

**唯一真值源纪律**：新增关系表先 `grep` 内核有没有；没有就加进内核，不要在学科里另抄一份。
六爻曾有 15 张表在三个文件里各存一份、其中八宫表取值互相矛盾（兑宫世次排错），
合一后 38 处副本归零。

学科若需要内核没有的表（如八字的藏干、十神、神煞），**加到内核并标注只有哪几科用**，
不要开第二个真值源。

## 三、口径与流派的显式化

同一套干支在不同流派下结果不同，必须做成参数而非注释里的说明：

| 分歧 | 本仓库默认 | 备选 | 影响 |
|---|---|---|---|
| 交节当日算旧月还是新月 | `boundary="day"` | `instant`（精确到时刻） | 月建、旺衰第一权 |
| 23:00–24:00 日辰 | 不作次日 | 换日派 `--zi-hour-type late` | 日辰、旬空 |
| 年界 | 立春 | 元旦 / 农历正月初一 | 年柱、以年支取数的起卦法 |

新学科沿用同一套默认值，否则跨科合参时命与卜说的不是同一个时间。

## 四、接入清单（照做即可）

1. 建 `Yi/disciplines/<科名>/`，内含 `SKILL.md`、`scripts/`、`references/`、`data/`
2. `SKILL.md` 只写该科内容；三条铁律（运算归代码 / 案例隔离 / 口径诚实）引 `Yi/AGENTS.md`，不复制
3. 实现 `chart`，并为其写金标准用例（照 `disciplines/liuyao/dev_tools/golden.py` 的思路：固定输入 → 全字段指纹）
4. 准备案例集：至少 10 例 `tune` + 5 例**未参与任何调参**的 `holdout`，
   每例必须有 `source`、可还原的起局信息、`expected` 要点；缺项的进 `excluded` 并写原因
5. 实现 `analyze` 时，每个判据都要能回答"哪本古籍的哪条法则"，答不上来就不要写
6. 实现评分器：**复用 `yishu_core.eval`**，
   禁止另写一套给分逻辑。指标必须报 n、报集合名、区分 strict/legacy
   质量门的进程壳（跑子进程 / 取指标 / 跑一套评测）**复用 `yishu_core.gate_kit`**，
   各科只在自己的 `dev_tools/check.py` 里声明口径（cwd、超时、argv 前缀、评测落盘路径），
   实现不得各写一份（2026-10-02e 前有 6 份互不相同的 subprocess 壳）
7. 加进 `tools/check.py` 的质量门，基线取首次数值，此后只准前进

> **豁免条款（2026-10-01c）**：**查表直录类学科**（现行仅 `lingqi`，断语直录古籍 124 课、
> 无干支历法运算）不设 `data/verdicts.json` 与 `data/cases/`，其断语源是
> `data/ketables.json`。根 `tools/check.py` 以 `TABLE_LOOKUP_DISCIPLINES`、
> `CONTRACT_EXEMPT_FILES` 两个常量认这一豁免，新增同类学科时照写即可，不必为了让门变绿
> 去造一份空的 `verdicts.json`。**但该类学科仍须在 `SKILL.md` 写明"本科不接内核、
> 书源为唯一真值源"**，以免后人误判为漏接。其余七科一律按 1–7 全条核。

## 五、验收标准（新学科）

- □ 一条命令从"所问之事"到单文件报告
- □ 质量门绿：历法自检 + 结构冒烟 + 用例 + 对齐分（tune/holdout 分别出分带 n）
- □ `grep` 全仓找不到第二份共用规则表
- □ 学科代码里没有成段断语字面量
- □ README 有真实截图与一条可复制执行的命令
- □ 没有任何"现实预测命中率"类表述
