## 一、系统总览（架构图所见）

```
求测者 → 网页端 AI ─┬─ 深链 → 通道A 纯前端(Pyodide) ─┐
                    └─ /yi 评论 → 通道B Actions ────┤
本地 CLI tools/report.py ──────────────────────────┤
                                                   ▼
                    request.py 请求归一（三执行器共用一份映射）
                                                   ▼
        四段契约 chart→analyze→narrate→render ⇄ yishu_core 内核（唯一真值源）
                                                   ▼
        命科(ming+ziwei) / 卜科(六爻+梅花+小六壬+择吉+大六壬+灵棋经)
                                                   ▼
        MD+HTML 报告 ──→ 交付A GitHub Pages ／ 交付B reports 分支+issue 回评
```

控制系统视角：**被控对象**是八科引擎；**传感器**是 golden 指纹 + 评测集（tune/holdout/wikisource）；
**执行器**是各科 `dev_tools/check.py` 与根 `tools/check.py --full`；**设定值**是基线分数与指纹。
整个系统的工程质量取决于这条闭环的灵敏度与不可欺骗性。

## 二、逐段评估

### 1. 输入侧 —— 结构良好，有两处尾巴

**已对的部分**：请求→命令行参数的映射只有一份（`core/yishu_core/report/request.py`），
三执行器共用，`tools/verify_web_parity.py` 用 10 正例 + 2 负例逐字节验收同源性——
这是教科书级的「单一入口 + 差分测试」。

**尾巴一 · 能力矩阵双轨**：通道 A 有意排除 liuren/lingqi（`tools/build_web.py:47`
注释 + 构建期 fail-fast 门），但这个事实只写在构建脚本注释里。外部读者（网页端 AI）
拿 `AGENTS.md` 读到「八科可用」时无从知道网页只能跑六科。**建议**：能力矩阵
（科 × 本地CLI/通道A/通道B/评测集）落一处权威表（`docs/AI-SOP.md` 或 `llms.txt`），
其余文档引用。这是 `docs/AUDIT.md` S-A4/C-2 的遗留项。

**尾巴二 · 输入协议无指纹**：引擎行为有 golden 指纹锁定，但 request.py 的输入协议
（参数名/别名/校验规则）没有对应机制——协议漂移只能靠同源验收间接发现。
**建议**：把 `request.py` 的参数表纳入 golden 快照（成本极低，`--full` 里加一条比对）。

### 2. 运算侧 —— 真值源纪律严格，复杂度分布失衡

**已对的部分**：内核唯一真值源 + 真值源门（函数内 dict/干支串/派生表三处盲区都查）
+ 学科复制 core 表即拒绝（ziwei/ming check 里有 CORE_TABLE 正则门）。依赖单向
disciplines→core 有门可查。

**失衡一 · 六爻占全库 72%**：liuyao scripts 37 文件 / 18,578 行，其余七科合计约 7,500 行。
复杂度集中不是错（六爻规则密度确实最高），但它使「读懂全仓」的成本近似于「读懂六爻」。
Phase 7 已瘦身 ~1,200 行，方向正确。**建议**：继续沿「门面 + 叶子模块」拆分，
把可外置的叙述逻辑移进 data/（每移一批跑一次 golden 验证零漂移），目标 scripts < 15,000 行。

**失衡二 · 「有传感器无判读」的骨架科**：大六壬（960 行）输出机械结构标签但无吉凶判读
（65 课目 + 《毕法赋》未落地，TECH-DEBT 已登记）；灵棋经（268 行）查表直录。
两科被通道 A 排除。系统工程上这是**故意降级的旁路支线**，不是缺陷——但要防止
「骨架」悄悄腐烂：它们的 check 门目前只验证结构。**建议**：给两科各加一条
「骨架完整度」自检（九宗门/十二天将输出字段数不变式），成本一次写好、长期防漂。

**已澄清的模式 · 调候双表不是违例**：core `TIAO_HOU`（51 格，有明文的格）与
`ming/data/tiaohou_quotes.json`（120 格，逐格引文）是「取值层/引文层」分层，
本轮已逐格比对 0 漂移。该分层模式值得在 `docs/ARCHITECTURE.md` 登记为**合法模式**
（取值唯一真值源在 core；引文/出处层在学科 data，由构建器从书源生成），
防止未来真值源门误伤。

### 3. 语料侧 —— 本轮主战场，闭环已补全

本轮实证的三个缺口与修复（详见 `docs/CHANGELOG.md` 2026-10-01k）：

| 缺口 | 性质 | 修复 |
|---|---|---|
| ziwei `命宫格局` 21 键文案中 7 键缺失、整块零消费 | 死语料 + 真缺口 | 补 7 组合格文案 + narrate 接线 |
| ming `verdicts.json` 纯骨架 | 命科措辞无真值源 | 建《子平真诠》格局引文库 + 调候原文上报告 |
| 六爻词典无天气占 | 取用错误（占雨落世爻兜底） | 补 9 键（雨→父母/晴→子孙），引文逐字核验，三集分数零漂移 |

以及一处减法：梅花 narrate 硬编码引文与 `basis_quotes` 构成双份真值源，
且两处出处都标错（实际属《卷二·体用》）——已统一为 data 单源 + 正确出处。

**遗留口径**：外部集 n 仍小（yingqi 2 / huozhulin 2 / wikisource 35+36），
57.1% 的 wikisource 读数只能当参照。**建议**（HANDOFF 已定，此处确认）：扩样靠换书
（卜筮正宗全本、易冒、易隐），**禁止**对现有集调参。

### 4. 质量门 —— 灵敏度高，但有一个已实证的方向性盲区

**已对的部分**：黑箱取证门（跑真实报告反查未外置句，本轮 0 漏外置）、
网页↔本地逐字节同源验收、黑箱回归 12/18 ≥ 基线 11/18、pytest、
克隆必红检查、断语键一致性检查——多层防御真实有效。

**盲区（本轮实证）· 审计是单向的**：verdict_audit 保证「报告里的句子 ⊆ 语料池」，
不保证「语料池 ⊆ 被消费」。ziwei `命宫格局` 整块文案零消费却全绿地过了所有门，
直到本轮手工排查才暴露。**建议**：加「语料消费审计」——golden 样例跑出的报告
对 verdicts.json 各键做覆盖率统计，零消费键要么接线要么标注 `unused` 并给理由。
这是本轮最有价值的门改进（把「发现死语料」从手工变成机械）。

**摩擦点 · 指纹粒度**：golden 指纹把 `narrate_sha` 与机械字段捆在一个 digest 里，
导致措辞层改动（本轮 3 科）也要重落整个基线，机械漂移与措辞漂移不可分别归因。
本轮三次 capture 都确认漂移仅 narrate_sha——规程可行但每次都要人眼确认。
**建议**：narrate_sha 单列一个 digest 字段，机械字段 digest 保持刚性、
措辞 digest 允许带理由滚动。改动小、归因收益大。

### 5. 输出侧 —— 双通道同源已锁死，回评文案在审计池外

**已对的部分**：render 单一出口；两道交付通道跑同一引擎；
`reports` 固定链接 + 逐次留档 + issue 回评三通道。

**尾巴 · 回评文案不受断语治理**：`tools/ci_deliver.py:66-67` 的口径声明
（对齐分/非命中率/专业意见）是 .py 内联字符串，不在 verdict_audit 的取证范围
（该工具只审 report.py 产物）。文案本身合规，但它若被人改动不会触发任何门。
**建议**：把回评口径句挪进共享语料（core report kit 或 data），ci_deliver 引用之；
或最低限度在 ci_deliver 加一条「口径句存在性」断言。

### 6. 反馈回路 —— 系统唯一的开环

现实效度的唯一证据通道是 `synthesis record-outcome`（占问事件回填 → 应期回收评分）。
当前 `disciplines/liuyao/data/feedback/` 为空——**回路开路，n=0**。
通道 B 的 issue 回评天然带回用户反馈，但没有接线到 event_logger/record-outcome。
**建议**（低优先、高价值）：report.py 输出尾部加一行固定引导
（「结果如何？可回复本 issue 或使用 record-outcome 回填」），通道 B 由 ci_deliver
在回评里附带；通道 A 无后端，可在报告尾部给出 JSONL 格式提示。
这不是功能开发，是把已有回路接上最后一米。
